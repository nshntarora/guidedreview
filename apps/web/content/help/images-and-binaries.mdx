# GitHub image diffs and binary file reviews

Not every changed file is a textual hunk. Guided Review still walks those files in the plan, but the diff pane behaves differently for images and for binary or elided content. Same behavior in the [Chrome extension](/docs/chrome-extension) and the [CLI](/docs/cli).

## Compare images on GitHub

To review an image diff on a GitHub pull request, open **Files changed** and find the modified image. GitHub's native image viewer offers three comparison modes for supported formats:

| Mode           | Use it to check                                                                |
| -------------- | ------------------------------------------------------------------------------ |
| **2-up**       | Both versions together, including dimension changes when the image is resized. |
| **Swipe**      | A particular region, moving the divider across the old and new image.          |
| **Onion skin** | Small position changes, adjusting opacity to overlay one version on the other. |

These are GitHub controls. Guided Review's overlay shows old and new previews; use the native viewer when you need swipe or onion skin.

GitHub supports viewing PNG, JPG, GIF, PSD, and SVG, but does not support comparing PSD versions. See [GitHub's image rendering and diff documentation](https://docs.github.com/en/repositories/working-with-files/using-files/working-with-non-code-files#rendering-and-diffing-images) for supported behavior.

## Image previews

When a changed path looks like an image the overlay can display (`png`, `jpg` / `jpeg`, `gif`, `webp`, `svg`, `bmp`, `ico`, `avif`, `tif` / `tiff`, and a few related types), the diff pane shows a **preview** instead of a line patch:

- **Added / removed** — one side’s image (or an empty side).
- **Modified** — old and new side by side in split view, or stacked depending on [unified / split](/docs/keyboard-shortcuts#diff-view).
- **SVG** — often reconstructed from the textual patch immediately; other formats load via the host (GitHub raw fetch on the extension, local blob on the CLI).

If the preview cannot load, you fall back to the binary empty state below.

## Check the asset in context

Suppose a PR replaces `logo.png` with a higher-resolution export. Start with the dimensions in GitHub's 2-up view, then check the crop and transparent edges. Use onion skin to inspect alignment if the artwork should stay in the same position.

Next, find the code that uses the asset. Does it set an explicit display size, or will the larger file change the layout? Open the relevant screen at the sizes the application supports. A comparison of two image files cannot establish how either one renders inside the application.

Record feedback with the asset path and the visible consequence: “The new logo includes extra transparent padding, so the header mark appears smaller at the same CSS width.” That gives the author something to reproduce. When there are no selectable diff lines, include the path in your [review summary](/docs/submit-review) rather than trying to attach a line comment in the overlay.

## Binary and elided files

Some files have no useful textual patch in the unified diff — true binaries, Git LFS pointers, or content GitHub / git elided as too large. For those, the pane shows:

```
(binary or elided — no textual diff available)
```

On a GitHub PR, Guided Review may offer a link into the Files changed tab for that path so you can inspect it on github.com. Locally, open the file in your editor or `git show` if you need the bytes.

## Comments and search

| Action                                              | Behavior                                                                                                  |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| [Comment mode](/docs/leave-comments)                | Needs selectable diff lines. Binary / empty image units usually have none — `c` has nothing to attach to. |
| [Diff search](/docs/keyboard-shortcuts#diff-search) | Binary / elided files still contribute **path** hits; there is no line content to match.                  |
| Image units with a preview                          | Treat like other units for navigation; line comments still need selectable text lines.                    |

## How the plan treats them

The pipeline still assigns these files to [review units](/docs/how-it-works#review-units). The model sees a short “binary or elided” marker in the prompt instead of dumped bytes ([How a review plan works](/docs/how-it-works)). Large or mostly binary diffs often produce thinner structure — see [Troubleshooting → Plan generation fails](/docs/troubleshooting#plan-generation-fails).

You still step past them with `←` / `→` so asset and lockfile noise stay in order with the rest of the change.
