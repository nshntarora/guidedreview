# How a review plan works

A short tour of the pipeline behind **Start Guided Review**. For the hands-on path, see [Your first review](/docs/first-review). Provider setup lives under [Configure AI provider](/docs/configure-provider).

<TocCard toc={toc} />

## Diff → plan

1. **Parse** — The unified diff is parsed into files, hunks, and lines. Every hunk gets a stable id (`filePath#index`) that the model must reference exactly.
2. **Prompt** — The parsed diff is rendered into LLM-readable text with hunk ids annotated.
3. **Annotate** — The background worker streams a structured review plan from [your provider](/docs/configure-provider) (API key never leaves the worker for LLM calls — [privacy](/docs/privacy-and-data)).
4. **Validate** — Each unit is cleaned against real file/hunk ids; hallucinated refs are dropped.
5. **Display** — The overlay resolves unit refs back to the real diff for rendering.

If no API key is configured, step 3 is skipped and a [local file-per-unit plan](#without-a-provider) is used instead. If annotation fails mid-stream, see [Troubleshooting → Plan generation fails](/docs/troubleshooting#plan-generation-fails).

## Review units

A **review unit** is a logical step in the plan: a title, intent context, and one or more hunk references. Production changes and tests are **separate** units — never mixed in one step. After each feature’s production unit(s), the matching tests unit follows immediately (not a single dump of all tests at the end). Tests steps show a flask icon next to the unit name in the sidebar and diff pane.

Units aim for a consistent structure on the same diff: same hunk partition, order, and change-vs-tests kind. Titles and wording may still vary slightly across models.

The first display step is a synthetic **PR description** unit built from page context, then the plan’s units. You step through them with the footer or [keyboard shortcuts](/docs/keyboard-shortcuts).

Summaries are optional guidance — you still judge the code ([FAQ](/docs/faq#does-the-ai-approve-prs)).

## Without a provider

If you start a review before [configuring an API key](/docs/configure-provider), Guided Review still opens:

- The diff is parsed and shown as usual.
- The plan is **one unit per changed file**, in the order files appear in the diff (tests still get the flask kind when the path looks like a test file).
- Unit titles are file paths; commentary is empty so the context panel can show the **Connect an AI provider** prompt instead of invented text.
- You can still navigate, [search the diff](/docs/keyboard-shortcuts#diff-search), [draft comments](/docs/leave-comments), and [submit](/docs/submit-review) once GitHub is connected.

Connecting a provider and starting again (or retrying when prompted) replaces that fallback with an AI-clustered plan for the current diff.

## Chunking large PRs

Large diffs are split **by file** into chunks (~60k characters each). A single file’s hunks are never split across chunks. Each chunk is annotated separately; unit ids are namespaced so multi-chunk plans don’t collide, then merged for the final plan.

That chunk size is why [model choice](/docs/configure-provider#pick-a-model) still matters on big PRs: **each chunk is a full model call**, so cost scales with diff size and model — see the [FAQ on cost](/docs/faq#will-this-run-up-my-api-bill).

## Streaming and validation

As text deltas arrive, complete units are extracted and validated. Progressive unit events update the overlay; a final done event carries the merged plan. Invalid structure or unknown hunk ids never reach the reviewer as broken links into missing code.

[Line comments](/docs/leave-comments) always attach to the real diff lines shown for a unit — not to model-invented code.

## What the model must not invent

| Allowed               | Not allowed                                         |
| --------------------- | --------------------------------------------------- |
| Order of review       | Fabricating file paths                              |
| Titles and commentary | Inventing hunk ids that aren’t in the prompt        |
| Grouping real hunks   | Replacing real diff lines with model-generated code |

If a unit only references invalid hunks after cleanup, it won’t be shown. That keeps the overlay honest even when the model is imperfect.
