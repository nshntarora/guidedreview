# AI code review that does not auto-approve

AI code review does not have to make the merge decision. A human-driven tool can use a model to group related hunks, order a walkthrough, and add commentary while leaving Comment, Approve, and Request Changes to the reviewer. That separation matters because a fluent summary can compress several product questions into one confident sentence. Use AI to navigate the diff; use the real code, tests, and product context to decide.

I don't want the model that explains a change to decide whether I should merge it.

You read “invalid input is rejected” in a summary. You see a passing test with a similar name. It feels like the question has been answered.

But which input? A missing field? An empty string? A value outside a range?

The summary has compressed three questions into one reassuring sentence.

## Who this is for

This category is for reviewers who want help reading a large or scattered change but do not want a bot's conclusion to become the approval. It suits repositories where a named person remains accountable for interpreting requirements, exceptions, and product tradeoffs.

It also fits authors checking agent-written work before asking someone else to review it. The useful output is a reading path and a set of precise questions, not a badge that says the code is safe.

## How human-driven AI review works

1. Parse the real diff into files and hunks.
2. Ask the model to group related hunks and suggest an order.
3. Resolve those references back to the real diff and discard invalid hunk identifiers.
4. Read production behavior, then tests, while checking commentary against the code.
5. Draft line comments where the contract is unclear.
6. Let the human select the review outcome.

That is the boundary Guided Review uses. The model plans structure and commentary only. It does not supply the code displayed in the overlay, generate a findings verdict, or select approval.

## What to include in the decision

Check intent, inputs, defaults, failure branches, authorization boundaries, callers, outputs, and tests. Ask whether the test would fail for the mistake you have in mind. A green suite and a confident summary are inputs to review, not substitutes for the reviewer understanding the change.

Keep comments specific. “Should an empty string be rejected too?” identifies a decision. “The validation seems wrong” merely transfers the investigation back to the author.

## What Guided Review lets the model do

The model groups hunks into review units, orders them, and adds commentary. The overlay resolves those references against the real parsed diff. It never displays model-generated replacement code as if it came from the patch.

[Invalid hunk references are dropped](/docs/how-it-works). The commentary can still be wrong, and the grouping can still be unhelpful. I can validate a hunk ID. I can't validate a product decision that way.

Production changes and tests appear as separate units. You can check the implementation before reading the test's account of it. The [AI-generated PR guide](/guides/review-ai-generated-pull-request) walks through that reading order.

## An Approve button still needs a person

The [Chrome extension](/docs/chrome-extension) can submit Comment, Approve, or Request Changes after you connect GitHub. You pick the outcome and what to send. Guided Review never auto-approves or rejects a PR.

The [CLI](/docs/cli) doesn't submit GitHub reviews. You leave local notes and can use Generate Prompt to copy them into a coding-agent prompt. AI structuring is opt-in. Both hosts support your own Anthropic, OpenAI, or Grok key, with no Guided Review backend receiving the diff.

If you want automated findings or a model-selected approval, a walkthrough won't replace that workflow. For a tiny patch you can read directly, you may not need one at all.

Before I approve that validation change, I want an answer about the empty string.

## When not to use this category

Guided Review is the worse choice if you want automated findings posted to every PR, a model-selected approval, or a required merge check. It intentionally leaves those jobs undone. A tiny patch that you can understand immediately may not need a structured walkthrough either.

For a local change, the CLI keeps notes in the running session and can Generate Prompt for a coding agent. For a github.com PR, the extension can draft comments and submit the outcome you choose. Start with [why the human review still matters](/docs/why), then choose the host in the [install guide](/docs/install).
