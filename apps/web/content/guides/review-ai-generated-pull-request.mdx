# How to review an AI-generated pull request

To review an AI-generated pull request, establish the intended contract before trusting the implementation, follow each changed value through related files, read production code before its tests, and check every summary against the real diff. Leave specific questions beside the relevant lines, then approve only when you can explain what changed and why. A structured walkthrough can reduce the file-order puzzle, but the reviewer still makes every judgment.

## Who this is for

This workflow is for the engineer whose name will appear on the review: a teammate reviewing an agent's PR, or an author checking agent-written work before requesting review. It is most useful when a change crosses types, callers, implementation, and tests.

It is not a special standard for machine-written code. The standard stays the same. The practical difference is that an agent can produce a large, consistent patch quickly, so surface consistency is weak evidence that the change matches the request.

## How to review the pull request

1. **Write down the intent.** Reduce the request to a behavior you can test or explain. Separate the stated outcome from the PR description's summary of the implementation.
2. **Find the contract.** Start with the type, interface, schema, or boundary where the change becomes observable.
3. **Follow related hunks together.** Trace the value through parsing, business logic, callers, error handling, and output. Do not let alphabetical file order define the investigation.
4. **Read production changes before tests.** Decide what the code does, then ask whether the test would fail for the mistake you are considering.
5. **Verify summaries against code.** A plausible explanation is a navigation hint, not evidence.
6. **Leave concrete questions.** Point to the branch, unit, default, or compatibility rule that needs an answer.
7. **Choose the review outcome yourself.** Submit only after unresolved questions are answered or explicitly accepted.

Guided Review is one way to get that sequence on a github.com PR. It groups related hunks into **review units** and keeps the real parsed diff on screen. The [Chrome extension docs](/docs/chrome-extension) cover installation and review submission. For work that has not become a PR, use the [local review guide](/guides/review-local-changes-before-pr).

## What to include in the review

Check the input and output contract, defaults, failure paths, callers, compatibility behavior, and tests. For a renamed value, ask whether only the name changed or the unit and meaning changed too. For a new option, check omission, empty values, and invalid values rather than only the happy path.

Keep tests and production changes conceptually separate. A test name may repeat the intended behavior while its assertion proves something narrower. Also scan files that consume the changed interface even if the agent did not mention them in its summary.

The model in Guided Review supplies structure and commentary only. Code shown in the overlay comes from the real diff, and [hallucinated hunk references are dropped](/docs/how-it-works). Commentary can still be wrong. Treat it like a map with fallible labels.

## A worked example: `timeout` becomes `timeoutMs`

Suppose an agent renames `timeout` to `timeoutMs`, updating a type, parser, two callers, and a test. The PR description says “updated callers,” and CI passes. That leaves three possible intents: a spelling change, a conversion from seconds to milliseconds, or a compatibility period supporting both names.

Start with the type and parser. Does the parser accept the old name? If both names are present, which wins? If neither is present, what default reaches the caller? Then follow both callers. A variable named `timeoutMs` can still contain seconds; a rename does not perform a conversion.

Read the test last. Passing `1000` and expecting `1000` might prove that a value survives the rename, but it does not prove a conversion or compatibility. Use an input that separates those behaviors: the old spelling for compatibility, five seconds for units, or an omitted value for the default.

A useful comment is specific: “This caller still passes seconds. Should the value be converted, or is the new name wrong?” The question identifies the contract and gives the author something concrete to answer.

## When not to use this workflow

For a three-line change whose behavior you already understand, the normal diff is usually enough. A structured walkthrough adds little when there are no relationships to reconstruct.

Guided Review is also the worse choice when you want a bot to produce findings, approve a PR, or act as a merge gate without you reading the change. It deliberately does none of those jobs. The extension can draft line comments and [submit a review you choose](/docs/submit-review), but it never chooses the outcome.
