# Review local git changes before opening a PR

Before `gh pr create`, I want to check two things: the committed branch against its intended base, and the working tree. They answer different questions.

You review the retry loop. It looks right. You remember adding a test for zero retries, so you open the PR.

Except the test is still uncommitted. You've filled a hole in the branch diff with something you remember from your editor.

## Choose the local diff you actually mean to review

Guided Review's CLI opens a browser walkthrough from a git repository. It needs Node.js 22 or newer:

```bash
npx @guided-review/cli
```

The package is `@guided-review/cli`; the binary is `guidedreview`. `npx guided-review` is a different tool.

Choose the scope before reading:

- **Branch vs base** shows committed work since the branches diverged. Use `--base` to select a particular base branch.
- **Uncommitted** shows staged and unstaged work against `HEAD`.
- **A specific commit** shows that commit's patch.

The [CLI reference](/docs/cli) covers the flags. Check untracked files too. A new test on disk isn't evidence that the PR contains it.

The initial walkthrough has one review unit per file and makes no model call. **Structure With AI** is an explicit action that sends a diff prompt to your configured provider for grouping and commentary.

## Read the retry contract before its test

Suppose the change adds `retries: 3`. Does that mean three attempts, or an initial attempt followed by three retries?

Read the option type, loop, and caller together. Then check zero. Does the request run once or not at all?

Now read the test. Does its expected count match that contract? Is it exercising the same path? If it's in the working tree, switch scope and inspect it there.

I prefer production changes and tests in separate review units. First work out what the loop does. Then decide whether the test would catch the off-by-one error.

## Send specific notes back to a coding agent

Leave a line note where the behavior is unclear. [Generate Prompt](/docs/generate-prompt) formats your notes into a prompt you can copy into a coding agent. It runs locally and doesn't make another model call. You choose where to paste it.

It doesn't run the agent or verify the fix. After the edit, read the new diff and run the repository's relevant tests, typecheck, lint, or build.

Notes live with the running server. Copy what you need before stopping it. The CLI doesn't submit GitHub reviews; the [extension](/guides/github-pr-review-extension) handles that once a PR exists.

## Check what will actually be published

Check that the branch includes the test, migration, generated files, configuration, or documentation the change depends on. Exclude local-only files. Run the checks after the final edit, rather than relying on a green run from before it.

The local server binds `127.0.0.1:7182` by default. AI structuring still sends code to your provider. There's no Guided Review backend receiving it, but [local review doesn't mean offline inference](/docs/privacy-and-data).

This is a local reading tool. There's no hosted team dashboard, automated findings, or merge gate. For an existing GitHub PR, I'd use the extension instead.

Before publishing the retry change, I'd check that the zero-retries test made it into the branch.
