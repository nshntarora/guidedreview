# How to review a large AI-generated PR

A 40-file PR changes a request schema, updates its callers, and replaces several tests. Reading it alphabetically makes you hold half the change in your head before you reach the implementation. Start by writing down the behavior that is supposed to change, then follow one value through the diff.

## Establish a boundary before reading

Read the PR description and identify the intended outcome, compatibility constraints, and evidence the author provides. Separate generated files, dependency updates, and mechanical moves from behavior changes. They still need checking, but they answer different questions.

If the author cannot explain which behavior belongs in this PR, ask for a smaller change. A walkthrough can order a diff; it cannot supply a missing requirement.

## Follow a contract across files

Suppose a request field changes from `timeout` to `timeoutMs`. Find its definition, its default, the caller that sends it, and the code that uses it. Check whether the change is a rename, a unit conversion, or both. A test that merely copies the new field name does not prove that old clients still work.

[Guided Review](/docs/how-it-works) groups related hunks into review units and orders them with short commentary. Use that plan to orient yourself, then check the real diff. If a caller seems absent, search the diff and inspect the repository outside the walkthrough. Unchanged code can still depend on a changed contract.

## Treat model limits as reading limits

Large diffs are chunked by file for AI structuring. A file is never split, so a single large file can exceed the usual chunk target. Provider limits can still reject the request. Separate chunks also limit the context available to each request; do not assume the model has connected every dependency across the PR.

Read the [chunking details](/docs/how-it-works#chunking-large-diffs). If structuring fails, use the file-by-file walkthrough or reduce the scope. Repeatedly requesting a plan adds provider usage without making the underlying change smaller.

## Check tests against a concrete failure

For each behavior change, name an input that should now behave differently. Read the relevant assertion and the production condition together. Run the focused tests using the repository's own commands; the walkthrough does not execute tests or prove correctness.

Leave comments where the evidence is missing. Distinguish a blocking compatibility concern from a question about intent. On GitHub, drafts remain local until you choose to submit them.

## Decide whether the PR is reviewable

A large PR may be coherent and still exceed the time you have to understand it. Ask for a split along behavior boundaries when necessary. Marking every unit read is navigation progress, not evidence of correctness.

Start with the [GitHub extension](/docs/chrome-extension), or [review local changes before a PR](/guides/review-local-changes-before-pr). You read the code and make the review decision.
